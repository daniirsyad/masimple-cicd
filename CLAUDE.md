# CLAUDE.md

Guidance for AI agents working in this repository.

## Tech Stack

- **Backend**: Flask (application factory pattern), Python 3.12
- **ORM/Migrations**: Flask-SQLAlchemy + Flask-Migrate (Alembic)
- **Database**: PostgreSQL (UUID primary keys everywhere)
- **Auth**: Flask-Login (session-based) + Flask-WTF (CSRF) + Werkzeug password hashing
- **Frontend**: Jinja2 templates + TailwindCSS 3 + daisyUI 4 (no JS framework); vanilla JS + vendored SortableJS for drag-and-drop. Vendored htmx with `hx-boost` on `<body>` makes links and forms load without a full page reload (server-rendered pages unchanged)
- **Deployment**: Docker (multi-stage: Node build for CSS, then Python/gunicorn), Docker Compose (`web` + `db` services)
- **Config/env**: `python-dotenv`, `.env` file
- **Tests**: pytest, hitting a real Postgres test DB (not sqlite/mocked)

## Architecture & Folder Structure

Flask **application factory** in [app/**init**.py](app/__init__.py) (`create_app`), extensions instantiated in [app/extensions.py](app/extensions.py) (`db`, `migrate`, `login_manager`, `csrf`).

```
app/
  blueprints/<name>/{routes.py, forms.py, __init__.py}   # one blueprint per feature: auth, main, users, roles, permissions, menus, logs
  models/                                                 # one file per table: user, role, permission, menu, activity_log
  utils/
    decorators.py     # @permission_required(code), @role_required(name)
    menu_builder.py   # builds sidebar/navbar tree, injected via context_processor into every template
    logger.py         # log_activity(...) writes to ActivityLog
  templates/<blueprint>/*.html, templates/partials/{navbar,sidebar}.html, templates/base.html
  static/src/input.css   -> built into static/dist/output.css (Tailwind/daisyUI) — dist/ is generated, not committed
  static/vendor/sortablejs/Sortable.min.js  # manually vendored copy of the npm package
migrations/          # Alembic, managed by `flask db migrate/upgrade`
seeds/                # seed_admin.py (creates the one Super Admin), seed_menu.py (default menu tree)
tests/                # pytest, one file per feature area
config.py             # Development/Production/Testing config classes, selected via FLASK_ENV
```

RBAC model: `User` → `Role` → many-to-many `Permission` (via `role_permissions` table). Permissions are string codes like `user.create`, `menu.edit`, `logs.view` — routes are protected by permission code, not role name.

Menus (sidebar/navbar) are DB-driven (`Menu` model), rendered dynamically per user via `menu_builder()`, **not** hardcoded in templates. The open group is the one holding the active item (`_active_url()` in `menu_builder.py`: the longest menu URL the path equals or sits under). Groups are an exclusive `<details name="sidebar-accordion">` set, and htmx's body swap briefly holds old and new sidebars, which closes the new open group; `sidebar.js` reopens `details[data-sidebar-current]` on every page, so keep that attribute on the active group.

## Entry Points

- [run.py](run.py) — dev entry point, calls `create_app()` from [app/**init**.py](app/__init__.py)
- [app/**init**.py](app/__init__.py) `create_app()` — registers all extensions and blueprints; this is where new blueprints/extensions must be wired in
- [entrypoint.sh](entrypoint.sh) — container startup: wait for DB → `flask db upgrade` → run seed scripts → `gunicorn run:app`
- Blueprints are registered with explicit `url_prefix`s (e.g. `/users`, `/roles`, `/menus`) except `auth` and `main`

## Conventions

- Blueprint package = `<name>_bp`, one `routes.py` + `forms.py` (Flask-WTF) per blueprint
- All model PKs are `UUID` (`sqlalchemy.dialects.postgresql.UUID`), generated with `uuid.uuid4` default — not integer autoincrement
- Route handlers: guard with `@permission_required("<resource>.<action>")` from [app/utils/decorators.py](app/utils/decorators.py); call `log_activity(action=..., target_type=..., target_id=..., description=...)` from [app/utils/logger.py](app/utils/logger.py) after any create/update/delete/login/logout
- Users support both a soft-delete toggle (`is_active=False`, via `toggle_active`) and a hard delete (`delete_user`). Hard delete (self included: it signs you out) first nulls every column that references the user (activity/error logs, `created_by`, `requested_by`, `triggered_by`, `built_by`, the security contact) and drops their reset tokens and manifest access grants, so history and attribution survive instead of failing on the FK or cascading. A new FK to `users.id` must be added to that list in `delete_user`
- **Hide actions the user can't use**: wrap each create/edit/delete/run button *and* its modal in `{% if current_user.has_permission("<code>") %}`, using the same code as the route's `@permission_required`. A page someone can only view must not offer actions that would 403. Where reading the data is still useful (Deployment Manifests' YAML), show a read-only "View" modal (`<fieldset disabled>`) instead. `tests/test_view_only_pages.py` + the `perm_client(*codes)` fixture cover this
- A 403 never shows Flask's bare page: the app-wide handler in `app/__init__.py` renders `errors/403.html` (reason + Back button, status stays 403), or returns `{"ok": false, "error": ...}` JSON for `fetch()` calls (`/api/` paths, JSON bodies, or `Sec-Fetch-Mode` other than `navigate`). `permission_required` puts a readable reason in it, built from the `Permission.description`
- **List rows** on Builders, Deployment Manifests, Versions, Registries, Dockerfiles, Deployment Servers, GitHub connections, Workflows (list, steps), Users, Roles, Permissions, AI settings, the cluster pages with Edit/Delete (namespaces, secrets, configmaps, ingresses, network policies) and every Archived page (`archived_row` macro) share one style. History/log pages keep their column tables but print statuses through the `status_word` filter ([app/utils/status_words.py](app/utils/status_words.py); `workflows.js` has a twin map for the run page): never print a raw code like `partial_failure`. Shared macros in `partials/_macros.html`: `entry_actions` (ghost Edit + ⋯ with Archive/Delete), `status_line` (dot or spinner + phrase + time ago), `rail_class` (status -> `entry-rail-*`), `more_menu`. A new list page of this kind uses them and `table entry-table`. Reorderable lists number rows with `.ordered-rows` / `.row-order` (CSS counter). Builders/Manifests specifics (`builder_row`/`manifest_row` macros, CSS in `input.css`): a row is `entry-row` plus one `entry-rail-*` state class (success/error/warning/building) shown as a bar on its left edge; line 1 is the name, line 2 a plain sentence of what it does; state comes next (last build, or a `server-lamp` per target server, lit = deployed); then one primary button, `Edit`/`View` as `btn-ghost`, and everything rarer (Archive, Delete, Restart, Stop) in the `more_menu` ⋯ macro. Keep the JS hooks (`.builder-row`, `.manifest-row`, `data-*`, `.build-one-btn`, `.deploy-one-btn`, `.update-one-btn`, `.restart-one-btn`, `.stop-one-btn`, `.drag-handle`) when changing them. These tables have no `overflow-x-auto` wrapper (it would clip the ⋯ menu); below 640px `.entry-table` rows stack instead
- Templates extend `base.html`; use daisyUI component classes (`alert alert-error`, `badge-success`, etc.) and Tailwind utilities
- **Jinja gotcha**: never write `{% if %}...{% endif %}` inline inside an HTML tag's attribute list — the workspace's HTML formatter corrupts it. Use a single expression instead: `{{ 'selected' if cond else '' }}`
- **Jinja gotcha**: the body of a `{% call %}` block (and other literal template text) is raw HTML, not autoescaped — a placeholder like `<app-deployment>` inside a `<pre>` is parsed as a tag and vanishes. Write `&lt;...&gt;`
- **daisyUI gotcha**: `.collapse` is `display: grid; overflow: hidden`, so wide content (a long `<pre>`) grows the column and gets clipped instead of scrolling. Add `grid-cols-1` (`minmax(0, 1fr)`) to the collapse element
- **YAML editors**: a page with a YAML textarea gives it class `yaml-content-input`, includes `partials/_yaml_editor_scripts.html` and calls `YamlEditor.initYamlEditor(textarea)` ([app/static/js/yaml_editor.js](app/static/js/yaml_editor.js)), which adds the wrapper, status bar (cursor position, key hints) and Full screen button. Don't hand-write those per page. A page with an editor in each row's modal uses `YamlEditor.lazyYamlEditor(textarea)` instead (builds it when the dialog first opens, returns a getter): 52 eager editors froze Deployment Manifests for 5 s
- **Static files** are cached by browsers for a year; `url_for('static', ...)` adds `?v=<mtime>` so changes still load. Always link static files with `url_for`, never a hand-written `/static/...` path
- **Per-request caching**: `per_request(key, fn)` ([app/utils/request_cache.py](app/utils/request_cache.py)) computes once per request (setup status, `get_system_config()`, the review badge); outside a request it computes every time. Every response's `Server-Timing` header shows its server time and SQL query count. List pages load related rows for all rows at once (eager loads, grouped counts, one query per relationship), never inside the row loop or template; a list page added to `LIST_PAGES` in `tests/test_page_performance.py` is checked for that. A page must not wait on an outside system (GitHub, kubectl, a registry) before sending HTML: load that part afterwards with `hx-get` + `hx-trigger="load"` (GitHub's "Available to register"), or put `@loading_page_first("...")` under the route's `@permission_required` (the cluster pages)
- Flash categories map directly to daisyUI alert classes (`success`, `error`, `info`)
- **Page scripts under hx-boost** ([app/static/js/page.js](app/static/js/page.js)): htmx swaps `<body>`, so `DOMContentLoaded` fires once per real load and timers/listeners outlive their page. Start page JS with `onPageReady(() => {...})`, never `DOMContentLoaded`; poll with `pageInterval(fn, ms)` (it also pauses while the tab is hidden), never a bare `setInterval`; give window/document listeners and polling `fetch()` `{ signal: pageSignal() }`; stop anything else (EventSource, chained `setTimeout`) with `onPageLeave(fn)`; re-fetch the page with `refreshPage()`, not `location.reload()`. Scripts loaded once in `<head>` (sidebar/theme/modal-form) use `onEveryPage(fn)`. A page's `{% block extra_head %}` is not loaded on htmx navigation, so shared CSS goes in `base.html`'s head. A form whose submit JS handles itself (`preventDefault` + fetch) needs `hx-boost="false"`, since htmx submits it anyway; for the same reason, don't sync a field into a form on `submit` (the YAML editor saves on every change instead). Modal-on-validation-error uses `<main data-open-modal>`, not `<body>`
- **Loading feedback is automatic** ([app/static/js/loading.js](app/static/js/loading.js), loaded in `base.html`'s head): every htmx form submit puts a spinner on (or, for WTForms' `<input type="submit">`, next to) the button that submitted it and disables it until the response; every htmx request longer than 300ms shows a bar at the top (`html.page-loading`, CSS in `input.css`). Don't add per-page spinners for forms. Opt a button out with `data-no-busy`. A page script doing its own `fetch()` uses `setBusy(button, true/false)` around it, and `showLoading(el, "Doing x...")` for a status line the result will overwrite

## Business Rules / Domain Logic

- **No public signup** — users are only created by an admin via User Management; the one initial Super Admin comes from `seeds/seed_admin.py` (`is_system=True` role; it can be deleted, and a restart re-runs the seed, which recreates it and gives a role-less admin user it again)
- **Menus have max nesting depth of 1**: a top-level menu can have children, but a child cannot have children of its own. Enforced server-side in [app/blueprints/menus/routes.py](app/blueprints/menus/routes.py) (`edit_menu`, `reorder_menus`) — do not remove this check, and any new menu-creation code must respect it
- A menu with no `permission_code` is visible to everyone; otherwise the viewer needs that permission (see `_visible()` in [app/utils/menu_builder.py](app/utils/menu_builder.py))
- A menu that still has children cannot be re-parented (must stay top-level); deleting it deletes its children too
- **Anything can be deleted; the only gate is the route's permission.** No delete is blocked by being in use, in a running job, a system role, your own account or the last admin. Delete routes follow one pattern: (1) fail the item's still-*queued* work with a reason (`fail_queued_builds` in [app/services/build/worker.py](app/services/build/worker.py), `fail_queued_executions` in the deploy worker, `fail_active_runs` in the workflow worker; running work finishes or fails on its own), (2) **unlink** dependents, never delete them (`unlink_builders` in [app/utils/deletion.py](app/utils/deletion.py)), (3) null history rows' link and save the name in a `*_name` column (`ImageBuild.builder_name`, `BuildBatch.version_name`, `DeploymentExecution.manifest_name`/`server_name`, `WorkflowRun.workflow_name`; `WorkflowStepRun.workflow_step_id` is just nulled). Readers use the `*_label` properties (`image.builder_label`, `batch.version_label`, `execution.server_label`/`manifest_label`, `run.workflow_label`, which print "name (deleted)") and `run.is_accessible_to(user)`, never `run.workflow.name`. Each page computes a `delete_impacts` dict shown in the confirm via the `delete_impact` macro; Archive sits next to Delete as the soft option
- A Builder whose Version/Repository/Registry/managed Dockerfile was deleted keeps an empty link: `Builder.missing_links()` lists them, the Builders page shows "Needs a new X", and every build path (web route, bots' `_builder_still_buildable`/`_builders_in_group`, workflow `_start_step`/`approve_awaiting_step`, the worker's `_run_build`) refuses it until edited. Deleting a Builder drops its manifest placeholder bindings and workflow-step selections; deleting a server drops it from manifests' targets; deleting a manifest drops it from workflow steps and leaves whatever it deployed running on the cluster; deleting a role leaves its users with no role
- Every login/logout/failed-login and every create/update/delete on users/roles/menus should write an `ActivityLog` row
- **Helm manifests** (`DeploymentManifest.source_type == "helm"`, [app/services/deployment/helm.py](app/services/deployment/helm.py)): `yaml_content` is the values file. Stop/Restart/status act on the release recorded on the execution (`helm_release_name`/`helm_namespace`), never the manifest's current fields; the form blocks changing type/release/namespace while deployed. Every `helm` call runs in a fresh temp HELM_*_HOME with passwords over stdin. Production runs Helm 4 (Dockerfile) while a dev machine may have Helm 3: only use `helm` commands and flags both have (Helm 4's `helm list` has no `--all`). Only `kube` servers can run Helm. Chart source is a repo or an uploaded `.tgz` or `.zip` (a zip is repackaged in memory into the `.tgz` `helm package` would make, deterministically so the same zip keeps the same checksum: `load_chart_upload()`/`zip_to_chart_tgz()`; only the `.tgz` is stored) (`HelmChartUpload`, bytes in Postgres, every version kept, unique per manifest+version and never replaced with different contents); an upload-source manifest deploys the upload whose `chart_version` equals its `helm_chart_version` (no FK back). Uploads are checked by `read_chart_archive()` (in memory, never extracted) and deleted with their manifest
- **Version placeholders**: `{{SYS:VERSION[:key]}}` becomes the bound build's full image reference (`registry/repo:tag`); `{{SYS:TAG[:key]}}` only its tag (for charts with `image.repository`/`image.tag`). Both share one binding per key; `PLACEHOLDER_PATTERN` (groups `kind`, `key`) and `placeholder_value()` in [app/services/deployment/resolver.py](app/services/deployment/resolver.py) are the single source, with a highlight twin in `yaml_editor.js`. "Find images" ([image_slots.py](app/services/deployment/image_slots.py)) turns existing images into placeholders by editing character ranges from the YAML parser's marks, so comments and layout survive
- **Detect on servers** ([app/services/deployment/detect.py](app/services/deployment/detect.py)): read-only check whether a manifest's app already runs on a `kube` server (YAML: `kubectl get -f - --ignore-not-found`, matched by kind/name; Helm: `KubernetesProvider.helm_release_info()` = `helm status -o json` (chart version from its `chart.metadata`, else `helm get metadata`) + `helm get values`; a "not found" release is missing), reading each placeholder's running value back by swapping placeholders for markers and following the same path in the live object (list items by `name`). Confirming re-checks and records a `DeploymentRun(action="detect", status="success")` with one successful execution per server, which every "is it deployed" rule already counts. Its `resolved_version_string` uses the deploy format (`key=image_ref`; an unknown value is `key=outside (x)`) so `get_available_update` works unchanged. Only a fully found app (all documents, Helm status `deployed`) can be marked. Gated by `deployment.deploy`
- **List search** (Deployment Manifests, Builders, Workflows): client-side, `list_search` macro in `partials/_macros.html` + `js/list-search.js`. It matches each row's lowercase `data-search` text (not the row's visible text, which includes button labels) and hides `[data-search-card]` cards with no matches; a new searchable field goes into that row's `data-search`. The query is kept across a same-page re-render (save/deploy redirect) and cleared when navigating to another page (`page.js` `beforeSwap`)
- **A build's git changes are captured at build time, never re-read later** (a force-push can make the old range unreadable): the worker saves `ImageBuild.commit_sha`, the `ImageBuildCommit` rows and `ImageBuild.changed_files` right after the repo sync, and writes the same data into the build log (`_record_commit_history`, `_format_changes` in [app/services/build/worker.py](app/services/build/worker.py)). All of it is best-effort: a git read failing must not fail the build. Pages that show a build's changes (Documentation, Images) get them from `commit_range_for_image()` in [app/services/build/history.py](app/services/build/history.py); `changed_files` is `None` for builds made before it existed, so templates must handle "not recorded"

## Do NOT Touch

- `app/static/dist/` — generated Tailwind output (built by `npm run build:css` / Docker asset stage), not hand-edited
- `app/static/vendor/sortablejs/Sortable.min.js` — vendored third-party file, copied from `node_modules`, not edited directly
- `app/static/vendor/htmx/htmx.min.js` — vendored htmx 2.0.11, copied from `node_modules/htmx.org/dist`
- `app/static/vendor/codemirror/` (incl. `addon/`) — vendored CodeMirror 5.65.21 core + addons, copied from `node_modules/codemirror`; keep addon versions matching the core
- `migrations/versions/*` — Alembic-generated migrations; create new ones via `flask db migrate`, don't hand-edit existing ones
- `migrations/env.py`, `alembic.ini`, `script.py.mako` — Alembic scaffolding
- `.env` — real secrets/DB credentials, never commit or print its contents

## Constraints & Gotchas

- The app runs behind an HTTPS reverse proxy: `ProxyFix` in `create_app()` trusts `X-Forwarded-Proto/Host/For` from `TRUSTED_PROXY_COUNT` proxies (default 1, `0` disables). Without it `url_for`/redirects come out `http://` and the browser blocks them as mixed content
- `kubectl`/`helm` reads for live status and Detect use `LIVE_STATUS_TIMEOUT_SECONDS` (30s, plus `--request-timeout` for kubectl) in [kubernetes_provider.py](app/services/deployment/kubernetes_provider.py); a slow cluster must not be reported as an error after a few seconds
- Test DB is a **separate real Postgres database** (`TEST_DATABASE_URL`, `TestingConfig`), not sqlite — tests require a reachable Postgres instance
- Run tests: `source .venv/bin/activate && python -m pytest tests/ -v` (needs `requirements-dev.txt`)
- A long-running `flask run` dev server does not always reload when _new_ blueprint modules are added (only edits to already-imported files trigger the reloader) — a full restart may be needed after adding a new blueprint
- A background job that must run once app-wide (not once per gunicorn process) starts with `become_leader(app, key)` ([app/utils/leader.py](app/utils/leader.py)), a Postgres advisory lock with its own key (917_442_101 Telegram, 102 Discord, 103 live-status poller). Queue workers don't need it: they claim with `FOR UPDATE SKIP LOCKED`
- CSRF protection (`Flask-WTF`) is active on all POST endpoints except under `TestingConfig`, where it's disabled
- Test fakes for the git provider (`_FakeGitProvider` in `tests/test_worker.py`, `_FakePreviewGitProvider` in `tests/test_builders.py`) are duck-typed, not `GitProvider` subclasses: when you add a method to `GitProvider` that the worker or preview calls, add it to the fakes too, or the tests silently take the best-effort "git failed" path
- `flask db migrate` compares against the local dev database, so that database must be at head first (`flask db current`). A new migration isn't applied to the dev database until `flask db upgrade`; the Docker entrypoint runs it on startup
- `reorder_menus()` expects a specific JSON shape (`{"top_level": [...], "children": {parent_id: [child_id, ...]}}`) and rejects payloads that would create depth > 1
- **Always update `SESSION_START.md`'s "Current state" section (and `APP_SUMMARY.md` if the change affects current-state architecture/features) at the end of any substantive session** — new feature, bug fix, architecture change, or DB/manifest edits made directly outside git — without waiting to be asked. Follow the existing style: a numbered list under a "This session's work" bullet, with prior sessions' bullets relabeled down a tier (see the file's own history for the cascade)

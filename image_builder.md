# Project Brief: Docker Image Builder Module for Flask App

## Context

I have an existing Flask application. I want to add a new module: a Docker image
builder tool that automates the pipeline from source code to a versioned, pushed
container image. Before writing any code, please explore the existing project
structure (routes, models, templates, auth system, config pattern) and follow its
existing conventions where possible. Ask me clarifying questions if something about
the current codebase is ambiguous.

## Core Pipeline

1. Pull source code from a Git repository (GitHub first, but design provider-agnostic).
2. Generate a semantic version string using this exact format:

   `{TYPE}.{MAJOR}.{MINOR}.{PATCH}.{UNIQUE_DATETIME}`

   Example: `DEV.7.14.27.2207261054`
   - `TYPE`: build type, user-selectable (e.g. DEV, STAGING, PROD)
   - `MAJOR.MINOR.PATCH`: standard semver — auto-increment from the last build for
     that type, or allow manual override
   - `UNIQUE_DATETIME`: format `YYMMDDHHmm`, generated at build time

3. Build a Docker image from the pulled source, using a Dockerfile at a configurable path.
4. Push the built image to a container registry (Docker Hub first, but design registry-agnostic).

## Architecture Requirements (must be provider-agnostic)

- Define a `GitProvider` abstract base class with a `GitHubProvider` implementation.
  Required methods: `clone_repo()`, `list_branches()`, `list_tags()`, `get_latest_commit()`.
- Define a `RegistryProvider` abstract base class with a `DockerHubProvider`
  implementation, built against the Docker Registry HTTP API v2 conventions so
  GHCR/Harbor/ECR can be added later without changing calling code.
  Required methods: `authenticate()`, `push_image()`, `list_tags()`.
- Use a factory/strategy pattern so the active provider is chosen via configuration,
  never hardcoded into business logic.
- Wrap the build step behind a `BuildEngine` interface, implemented first with the
  official `docker` Python SDK (docker-py), so it could later be swapped for
  Buildah or Kaniko (e.g. for daemonless/rootless builds).

## Pages / Routes

1. `/versions` — list all generated versions; filterable by type, date range, and
   source branch. Each row links to its full documentation detail page.
2. `/images` — list all built images with status (success / failed / in-progress),
   full version tag, image size, registry link, and timestamps.
3. `/builder` — configuration and one-click build page:
   - Select Git branch or tag
   - Select/override build type (DEV / STAGING / PROD)
   - Dockerfile path input (default: repo root)
   - Optional build args (key-value pairs)
   - Target registry selection
   - Single "Build" button that triggers the pipeline
   - A visible status area showing whether the build engine is free, currently
     building (with who/what is running), or how many builds are queued ahead
4. `/versions/<id>/documentation` — full-detail documentation view/edit page for a
   single version (see "Version Documentation" section below). This is where the
   mandatory metadata, AI-assisted description, and linked versions are shown and edited.

## Version Documentation (mandatory for every version)

Every version must have an accompanying documentation record. Treat a version as
incomplete until at least type, object, and description are filled in — surface this
visibly (e.g. a "documentation pending" badge) on `/versions` and `/images` until it's done.

Fields on the documentation record:

- **Built by** — the user who triggered the build. Auto-filled from the logged-in
  user/auth system, not manually entered.
- **Version** — the full version string. Auto-filled, read-only.
- **Branch name** — manual input (can default to the branch used for the build, but
  keep it editable).
- **Type** — manual selection from a configurable list, not a hardcoded enum. Seed it
  with: New Program, Update, Bug Fix, Hot Fix, Cherry Pick. Store it as a lookup table
  so new types can be added later (e.g. by an admin) without a code change.
- **Object** — manual input, but suggest existing values as the user types (autocomplete
  sourced from distinct `object` values already used in prior documentation records).
- **Description** — primarily generated by AI (see "AI Description Assistant" below),
  but always user-editable. The user can accept the AI draft as-is, edit it, or add
  their own notes on top before saving the final text.
- **Linked versions** — a version's documentation can reference one or more other
  versions it incorporates. Example: `QAS.1.1.1.111111` links to `DEV.1.1.1.11111` and
  `DEV.1.1.2.111111` because that QAS build bundles both of those DEV changes. This is
  a many-to-many relationship and fully manual/configurable — let the user search and
  pick which prior versions to link on this documentation page; don't try to auto-infer
  it from git history.

## AI Description Assistant

Add a description-generation panel (can be its own page or embedded directly in the
documentation form — whichever fits this project's UI better):

- Input: relevant build context available to you — commit messages since the last
  build on that branch, the branch name, the selected type, and the object field.
- Call the Claude API (Anthropic Messages API via the official `anthropic` Python SDK)
  to draft a description from that context. Check Anthropic's current docs for the
  recommended model at implementation time rather than hardcoding a model string, since
  the model lineup changes over time.
- Show the AI draft in an editable text area so the user can revise or append before
  saving — never save the raw AI output directly as final without the user seeing it first.
- Store both the raw AI draft (e.g. `ai_description`, for audit/traceability) and the
  final saved `description` separately.

## Concurrency Handling (single build at a time, no external broker)

Keep this lightweight — no Celery/Redis for now. Instead:

- Only one build may run at a time. Use a simple mechanism to enforce this, e.g. a
  Python `threading.Lock` plus a background worker thread that pulls jobs one-by-one
  from a `queue.Queue` (standard library, no external broker needed).
- When a user clicks "Build":
  - If the engine is idle, start the build immediately.
  - If a build is already running, add the request to the queue, tell the user their
    position in line (e.g. "You are #2 in the queue"), and notify them who/what is
    currently building if that info is available.
- Persist queue/build state in the database (not just in memory) so status survives
  a page refresh and is visible to every user looking at `/builder`.
- The frontend should poll a status endpoint every 2-3 seconds to update: current
  build progress/log tail, queue position, and a notification once the user's own
  queued build starts or finishes.
- Design this concurrency layer behind a small interface so it can be swapped for
  Celery/RQ later without touching the pipeline logic itself, in case build volume
  grows.

## Suggested Data Models

- `BuildVersion`: id, type, major, minor, patch, datetime_string, full_version_string,
  source_branch, source_commit, created_at
- `ImageBuild`: id, version_id (FK), status (`queued` / `running` / `success` / `failed`),
  registry_name, image_tag, image_size, build_log, requested_by, queue_position,
  started_at, finished_at
- `BuilderConfig` (optional, saved presets): id, name, git_provider, registry_provider,
  dockerfile_path, default_build_args
- `ChangeType`: id, name, is_active — seed with New Program, Update, Bug Fix, Hot Fix,
  Cherry Pick; must be addable later without a code change
- `VersionDocumentation`: id, version_id (FK, one-to-one with `BuildVersion`), built_by,
  branch_name, change_type_id (FK), object, ai_description, description, created_at, updated_at
- `VersionLink`: id, version_id (FK — the version being documented), linked_version_id
  (FK — a prior version it incorporates), note (optional), created_at

Adjust field names/types to match this project's existing model conventions.

## Security Requirements

- Store Git tokens and registry credentials in environment variables or a secrets
  manager — never hardcoded, never stored in plaintext in the database.
- Encrypt any credential that must be persisted.
- Reuse the app's existing auth/role system to gate who can trigger a build, if one
  already exists.
- Store the Anthropic API key (`ANTHROPIC_API_KEY`) used for the AI Description
  Assistant in environment variables the same way as other credentials — never in code
  or the database.

## Suggested Tech Stack

- Backend: Flask, SQLAlchemy
- Concurrency: Python standard library (`threading`, `queue`) — no external broker
  needed at this stage
- Git integration: GitPython or PyGithub
- Docker integration: `docker` (Docker SDK for Python)
- AI description generation: `anthropic` Python SDK (official Claude API client)
- Status updates: simple polling endpoint (JS `fetch` on an interval); Flask-SocketIO
  only if it's already used elsewhere in this project
- Frontend: match this project's existing templating/styling approach (Jinja2 or
  existing JS framework — check before introducing a new one)
